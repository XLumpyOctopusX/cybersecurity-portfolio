## Project Summary

This project documents my investigation of a simulated cybersecurity alert while completing TryHackMe's *Introduction to SIEM* room for ITECH1502 Cybersecurity Fundamentals at Federation University. I selected this activity because Security Information and Event Management (SIEM) tools are important in Security Operations Centres (SOCs), where analysts review logs and investigate possible threats.

During the exercise, I explored how SIEM systems collect information from hosts and networks and use detection rules to identify activity that may require attention. The practical scenario involved an alert associated with the process `cudominer.exe`. By reviewing the alert details, I identified the affected computer (`HR_02`), the associated user (`Chris`), and the detection rule that matched the word `miner`. I concluded that the alert was a true positive within the simulation.

Completing the room helped me understand how individual pieces of log information support an investigation. It also showed me why analysts must check evidence before deciding whether a security alert requires a response.

## Introduction

A SIEM system collects and analyses security information from different sources, helping analysts spot events that may indicate a cyber threat. This is useful in a SOC because organisations generate large amounts of security data, and investigators need a way to identify important activity without examining every record individually.

I used TryHackMe because it provides a guided environment in which I could practise these concepts safely. The activity was part of my learning about security operations, incident response, and SIEM technology.

## Problem and Challenge

The practical challenge was to investigate an alert generated by suspicious process execution. An alert by itself does not explain the full situation: an analyst needs to identify what triggered it, where the event occurred, and whether the available evidence supports the alert.

The activity therefore required me to examine information associated with the alert, connect the process to a user and computer, and decide whether the alert was a true positive or a false positive.

## Objectives

- Understand how a SIEM uses host-related and network-related data to support security monitoring.
- Investigate a suspicious process alert in a guided SOC-style exercise.
- Identify the process, user, and host associated with the event.
- Examine the detection-rule match and classify the alert using the available evidence.
- Reflect on how this workflow relates to an entry-level cybersecurity analyst role.

## Methodology

1. **Study the SIEM concepts.** I worked through the room's explanations of security logs, host-centric and network-centric information, log sources, and alerting.
2. **Open the practical investigation.** I followed the room's lab activity involving a simulated security alert.
3. **Identify the suspicious process.** I reviewed the alert information and found the process name `cudominer.exe`.
4. **Examine the related event.** I identified the associated user as `Chris` and the computer hostname as `HR_02`.
5. **Review the alert trigger.** I examined the detection rule and found that `miner` in the process name matched the rule, producing the alert.
6. **Classify the alert.** After reviewing the evidence presented in the exercise, I recorded the alert as a **true positive**.

These steps describe the guided TryHackMe simulation. I did not deploy a SIEM on a live organisational network.

## Reflection

### What did I learn about cybersecurity concepts and tools?

I learned that a SIEM is useful because it brings security information from different sources into a place where analysts can investigate activity. The exercise helped me understand the relationship between a suspicious process, a detection rule, a user, and a computer. Previously, these details seemed like separate pieces of information, but working through the alert showed me how they fit together.

The distinction between a true positive and a false positive was another important lesson. A rule can generate an alert when activity matches certain conditions, but an analyst still needs to review the context before deciding what happened. In this exercise, the available evidence supported a true-positive classification.

### How will this contribute to my professional growth?

I am interested in developing practical cybersecurity skills and working towards a role involving security operations. This activity introduced me to the sort of investigation a SOC analyst might perform: reviewing alerts, checking related evidence, and explaining a conclusion. It helped me connect concepts from university to an example of how organisations monitor their systems.

### What would I do differently next time?

One challenge was understanding how the individual alert details related to each other. I initially had to work out which information identified the process, user, and computer. Next time, I would use a more consistent checklist: establish what triggered the alert, identify the host and user, inspect the supporting event details, and then decide how the alert should be classified. I would also take screenshots throughout the investigation instead of relying mainly on the completion screen at the end. That would make it easier to explain and verify each step.

## Ethical and Professional Considerations

This project was completed in an authorised training environment. The results relate to a simulated investigation, not a real-world security incident. In professional practice, analysts should use only systems and data they are authorised to access, handle logs responsibly, protect personal information, and avoid drawing conclusions without sufficient evidence.
